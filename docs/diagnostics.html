:::meta description: Every diagnostic Tern reports: its severity, what triggers it, where it points, what happens to the content, the engine's message and hint, and the fix, each with a live example. ::: ::site-nav # Diagnostics {#top} ::toc Tern never drops what you wrote without telling you. When something is malformed, Tern keeps it visible where you wrote it and reports a *diagnostic*: a code such as `block.unclosed`, a severity, a message, a position and a hint that quotes the fix in Tern's own syntax. This page lists every diagnostic. For each one it says: - how serious it is; - exactly what triggers it; - where it points; - what happens to your content; - what the engine says, word for word; - how to fix it. Each code has a live example that triggers it, and a second one with the fix. Both are computed by the engine in your browser as you read: open an example to see its result, the HTML and the diagnostics. ## At a glance {#summary} The first 53 codes come from the parser and the transforms, so `tern.check`, `tern check` and your editor report them. Each code always has the same severity, with one exception: `head.script` is an info for a remote script and a warning otherwise. The six runtime codes are all errors, and `addon.remote` is an info. Severity decides how each tool treats a diagnostic: - `tern check` exits with 1 when it finds a diagnostic at or above `--fail-on`, which is `error` by default ([tools](tools.html#check)). - The console prints errors and warnings with `console.warn`, and infos with `console.info`. - The on-page panel opens itself when there is an error. - The language server sends severity 1 for an error, 2 for a warning and 3 for an info, which editors show as Error, Warning and Information. ### Positions {#positions} A position has a `start` and an `end`, each `{line, column, offset}`: - **line** is 1-based and counts *note lines*: line 1 is the first line after the `tern.js` line. - **column** is 1-based and counts UTF-16 code units, as JavaScript strings and the language server do. A tab counts as one column, and an emoji such as 😀 counts as two. - **offset** is the 0-based index into the note, after `\r\n` and `\r` have become `\n`. - **end** is exclusive: the column just after the last character. On this page, "at 1:15" means line 1, column 15 of the example. The sections below use three phrases: | Phrase | Means | |---|---| | the line | The column where the line's remainder starts: after any `>` quote markers, list-item indentation and footnote-definition indentation. Every line-level code points there. | | the id | The `#` of `#id`, or the first letter of `id=`. | | the first bad column | The first character the grammar rejects: in `{#k!}`, the `!`. | Here the closer is inside a list item inside a quote. Its remainder starts after `> - `, so the diagnostic points at column 5, not column 1: ```tern {.live expect="block.stray-closer"} > - ::: ``` **Note lines and file lines.** Your editor counts *file lines*, from the top of the file. A file line is the note line plus the number of lines up to and including the `tern.js` line, so with the usual one-line head, file line 2 is note line 1. Each tool says which it means: - `tern check` prints file lines, `note.html:2:9`. The message still cites note lines, as the engine wrote it. - The panel shows both: `line 1:9 (file line 2)`. - The language server sends file lines, converted to the editor's 0-based lines. - `tern.check`, `tern.parse` and `tern.diagnostics` hold note positions. - The codes that concern the `tern.js` line or the head (`doc.quirks`, `addon.failed`, `katex.unavailable`) are at line 0, column 0, the line before the note's first. The panel shows them as `the tern.js line (file line 1)`. For example, `tern check` on a note whose first line is the usual head: ```sh $ tern check note.html note.html:2:9: error block.opener-junk: this is not part of the opener; it is shown as an error paragraph a title goes in brackets: `:::note[Danger]` tern check: 1 note: 1 error, 0 warnings, 0 infos ``` :::note In the browser, the file line can read too low when the head puts `` and `` on lines of their own: the HTML parser drops the line breaks after them before tern.js can count them. With both on lines of their own, the panel's file line is 2 lower than the real one. `tern check` and the language server count from the file itself and are exact. ::: ### Where diagnostics appear {#console-and-panel} The same diagnostics reach six places: | Where | What you get | When | |---|---|---| | The console | One collapsed group, `tern: N problems` | Every time a note renders | | The panel | A list after the note | On `file:` and local hosts, or with `data-diagnostics`; never with `data-quiet` | | `tern.diagnostics` | A live array | On the page | | `tern.on('diagnostic', fn)` | Each runtime diagnostic as it is reported | On the page | | `tern check` | `file:line:col: severity code: message` | On the command line | | The language server | `textDocument/publishDiagnostics` | In your editor | **The console.** When a note has rendered, tern.js prints one collapsed group named `tern: N problems`, even when N is 0. Each is loud, and each leaves the rest of the note intact. **1. Braceless attributes.** Attributes always go in braces. This example uses the demo schema, which declares `theorem` ([the demo schema](schema.html#demo-schema)): ```tern {.live schema=demo expect="block.opener-junk"} :::theorem[T] #rn .big Every linear map has a kernel. ::: ``` The engine reports `block.opener-junk` (error) at 1:15: - **Message:** `this is not part of the opener; it is shown as an error paragraph` - **Hint:** `` attributes go in braces: `:::theorem[T]{#rn .big}` `` The block still opens as a theorem, and the junk is shown in red as its first paragraph. Put the attributes in braces: ```tern {.live schema=demo} :::theorem[T]{#rn .big} Every linear map has a kernel. ::: ``` **2. A forgotten closer.** Here `:::proof` has no closer, and `:::/section` closes the section: ```tern {.live expect="block.unclosed"} :::section :::proof The proof. :::/section ``` The engine reports `block.unclosed` (error) at 2:1: - **Message:** `` `:::proof` opened on line 2 is still open at line 4 `` - **Hint:** `` add `:::` or `:::/proof` `` The error lands on the proof, line 2, not on the section: the named closer closed both, and only the proof was missing its closer. Add it: ```tern {.live} :::section :::proof The proof. ::: :::/section ``` **3. A blank line in `$$`.** TeX forbids blank lines in display math, so a blank line ends the block: ```tern {.live expect="math.unclosed"} $$ a^2 + b^2 = c^2 ## Next section ``` The engine reports `math.unclosed` (error) at 1:1: - **Message:** `` `$$` opened on line 1 ends at the blank line on line 3 without a closing `$$`; TeX forbids blank lines in display math `` - **Hint:** `` add a line holding only `$$` `` The source of the equation is shown in red, and the heading after it survives. Close the block: ```tern {.live} $$ a^2 + b^2 = c^2 $$ ## Next section ``` ## Blocks {#blocks} These concern containers (`:::name` … `:::`), their closers and the spelling of their first line. See [containers](syntax-blocks.html#container) and [closers](syntax-blocks.html#closer). ### `block.unclosed` {#block-unclosed} **Error.** A container is still open when its parent or the note ends. - **Trigger.** A `:::name` container has no closer before one of these: - the end of the note; - the end of the quote, list item or footnote definition it is in; - a named closer, `:::/outer`, that closes a container around it. Every container opened inside that one and still open is unclosed. - **Position.** The opener, from its first colon to the end of the name. - **Content.** Nothing is lost, but the meaning changes: the block runs to where it was closed, so everything after the missing closer is inside it. - **Message.** It names the line where the container was found still open. The hint adds a reason when the engine knows one: a fence or a raw `` counts); - a generic block-level or custom element whose openings and closings never balance. A comment or raw-text block runs to the end of the innermost quote, list item or footnote definition, or to the end of the note, through `:::` lines, since it may legitimately hold them. A generic block also stops at the first `:::` opener or closer line, which is then read normally. - **Position.** The first line of the block. - **Content.** - An unclosed comment or raw-text block is **not** emitted as HTML: in the browser it would turn the rest of the page into a comment, a script or a stylesheet. It is shown as escaped source in a `
`, from its first line to the last line it held.
  - An unclosed generic block is still emitted as raw HTML, up to where it stopped. The browser then balances the tags itself, which can change what ends up inside what.
- **Hint.** The end tag to add.

### `tag.not-allowed` {#tag-not-allowed}

**Warning.** `tag=`, or a schema's `tag`, names an element the level cannot be.

- **Trigger.** Two cases:
  - **Outside the allowlist.** `{tag=x}`, or a schema entry's `tag`, names an element outside the level's allowlist: a phrasing element on a container, a flow element on an inline element, `table` on a leaf. `a`, `img` and `br` are left out on purpose, since links, images and `\` spell them. A custom element is in no allowlist: write it as the name, `:::my-widget`. A reserved element is [`name.reserved`](#name-reserved) instead.
  - **Off a named element.** `{tag=x}` anywhere but on `:::name`, `::name` or `:name[…]`: on a span, link, image, code span or heading, or on a block through an attribute line.
- **Position.** The `tag` key; for a schema's `tag`, the name.
- **Content.** Outside the allowlist, the `tag` is ignored, and the next rule decides the element: the schema's `tag`, a custom-element name, the allowlist, then `div` or `span` with the name as class. Off a named element, the `tag=` is dropped.
- **Hint.** Elements this level can be.

```tern {.live expect="tag.not-allowed"}
:::aside{tag=span}
Aside text.
:::
```

The engine reports `tag.not-allowed` (warning) at 1:10:

- **Message:** `` `tag=` asks for `span`, which a container cannot be; the next rule decides ``
- **Hint:** `choose a flow element such as section, aside or div`

**Fix.** Choose an element the level allows. Here the name alone is enough, since `aside` is in the container allowlist:

```tern {.live}
:::aside
Aside text.
:::
```

On an inline element:

```tern {.live expect="tag.not-allowed"}
A :note[remark]{tag=div}.
```

The engine reports `tag.not-allowed` (warning) at 1:17:

- **Message:** `` `tag=` asks for `div`, which an inline element cannot be; the next rule decides ``
- **Hint:** `choose a phrasing element such as kbd, abbr or span`

Off a named element, on a span:

```tern {.live expect="tag.not-allowed"}
Press [Ctrl]{tag=kbd}.
```

The engine reports `tag.not-allowed` (warning) at 1:14:

- **Message:** `` `tag=` applies only to `:::name`, `::name` and `:name[…]`; it is dropped here ``
- **Hint:** `` remove it; to choose the element, name it: `:kbd[…]`, `::video[…]`, `:::aside` ``

**Fix.** Name the element instead:

```tern {.live}
Press :kbd[Ctrl].
```

**Related.** [`name.reserved`](#name-reserved), [`table.body`](#table-body), [`leaf.void-content`](#leaf-void-content).

### `table.body` {#table-body}

**Warning.** A `:::table` whose body is not exactly one pipe table.

- **Trigger.** A container whose element would be `table`, by its name, `tag=table` or a schema's `tag`, and whose body is anything but one pipe table: paragraphs, two tables, a raw ``.
- **Position.** The name.
- **Content.** It becomes a `div` with its body as written. With a schema, it keeps its label and counter ([table captions](elements.html#table-caption)).

```tern {.live expect="table.body"}
:::table[Phases]
Two phases, described in prose.
:::
```

The engine reports `table.body` (warning) at 1:4:

- **Message:** `` `:::table` becomes a 
 only when its body is exactly one pipe table; this one is a div ``
- **Hint:** ``put one `| … |` table in the block, or use another name``

**Fix.** Put exactly one pipe table in it; the title becomes the `
`:

```tern {.live}
:::table[Phases]
| Phase | Weeks |
|---|---|
| P1 | 2 |
:::
```

A raw `` keeps its own `
`; write it without the container.

**Related.** [`tag.not-allowed`](#tag-not-allowed).

### `name.unknown` {#name-unknown}

**Info, with `strict` only.** A name has no schema entry and names no element.

- **Trigger.** Only when the schema has `strict: true`. A container, leaf or inline name that has no schema entry, is not a valid custom-element name and is not in the level's allowlist, so it falls back to `div` or `span`. A name the schema declares never gets it, even without a `tag`. Names are case-sensitive, so `:::Aside` is unknown.
- **Position.** The name.
- **Content.** The same as without `strict`: `div` (container, leaf) or `span` (inline), with the name as its class.
- **Hint.** To check the spelling, or declare the name.

The live examples on this page run without `strict`, so this one shows the fallback with no diagnostic:

```tern {.live}
:::theorm
A typo.
:::
```

`strict` is a field of the schema. A note turns it on in a head script before the `tern.js` line ([`window.TERN`](schema.html#window-tern)):

```html

```

An add-on listed in `data-use` can turn it on too, with `tern.schema.strict = true`, since add-ons run before the note is parsed. The note's own setting wins, so `strict: false` in `window.TERN.schema` turns it off whatever an add-on says. The browser, `tern check` and the language server all honour it.

With it, the example above reports, at 1:4:

- **Message:** `` `theorm` has no schema entry and names no element, so it is a div ``
- **Hint:** `check the spelling, or declare the name with tern.block, tern.leaf or tern.inline`

Under node, pass it in the schema: `tern.check(source, {schema: {...tern.schema, strict: true}})`.

**Fix.** Correct the spelling, or declare the name ([schemas](schema.html#schema)).

**Related.** [`name.reserved`](#name-reserved), [`tag.not-allowed`](#tag-not-allowed).

## Ids and references {#ids-and-references}

These concern [ids](elements.html#ids) and [references](elements.html#references): `@id` and fragment links `[text](#id)`.

### `id.invalid` {#id-invalid}

**Warning.** An id that is not a valid HTML id.

- **Trigger.** An `id=` value that is empty or holds whitespace, as `id=""` or `id="a b"`. A `#id` cannot be either.
- **Position.** The first letter of `id=`.
- **Content.** The id is dropped. A heading that loses its id gets its slug instead.

```tern {.live expect="id.invalid"}
## Results {id="final results"}
```

The engine reports `id.invalid` (warning) at 1:13:

- **Message:** `"final results" is not a valid HTML id: it is empty or holds whitespace, so it is dropped`
- **Hint:** `write an id without spaces: {#my-id}`

**Fix.** An id has no spaces:

```tern {.live}
## Results {#final-results}
```

**Related.** [`ref.unreferenceable`](#ref-unreferenceable), [`id.duplicate`](#id-duplicate), [`attr.malformed`](#attr-malformed).

### `id.duplicate` {#id-duplicate}

**Warning.** Two elements have the same id.

- **Trigger.** Two *fixed* ids collide. Fixed ids are those you wrote, with `#id` or `id=`, anywhere, and the footnote ids `fn-LABEL`, `fnref-LABEL` and `fnref-LABEL-N`. Heading slugs never collide: a slug that is taken becomes `kernel-2`, silently.

  Tern's own ids are taken before any of these: `tern-style`, `tern-color-scheme`, `tern-source` and `tern-diagnostics`, which tern.js gives elements of its own in the page. An id you write that is one of them gets this diagnostic once, and a slug yields to them silently (`tern-style-2`).
- **Position.** The id, at every element that has it: the first and each later one.
- **Content.** The first keeps the id, and references resolve to it. Each later element drops its `id` attribute, which keeps the HTML valid. A heading that loses its id gets its slug instead.
- **Message.** The first says the id is used again and this element keeps it; each later one says it is already used and this element drops it.

```tern {.live expect="id.duplicate id.duplicate"}
## One {#part}

## Two {#part}
```

The engine reports `id.duplicate` (warning) at 1:9 and 3:9:

- At 1:9, the message `the id "part" is used again on line 3; this element keeps it`, with the hint `give each element its own id`.
- At 3:9, the message `the id "part" is already used on line 1; this element drops it`, with the hint `give each element its own id`.

**Fix.** Give each element its own id:

```tern {.live}
## One {#part-one}

## Two {#part-two}
```

One of Tern's own ids:

```tern {.live expect="id.duplicate"}
{#tern-style}
A paragraph.
```

The engine reports `id.duplicate` (warning) at 1:2:

- **Message:** `the id "tern-style" belongs to tern itself, which gives it to an element of its own in the page; this element drops it`
- **Hint:** `choose another id`

An id you write wins over a heading's slug, with no diagnostic:

```tern {.live}
## Kernel

:::definition{#kernel}
The kernel of a map.
:::
```

**Related.** [`footnote.duplicate`](#footnote-duplicate), [`id.invalid`](#id-invalid).

### `ref.dangling` {#ref-dangling}

**Warning.** A reference points at no id.

- **Trigger.** A reference `@id`, or a fragment link `[text](#id)`, whose id names nothing in the note. The usual cause is a mention, such as `@alice`, or a typo.
- **Position.** The reference, with its group; for a link, its `[`.
- **Content.** `@id` stays literal text, and a group after it is consumed. A fragment link stays a link.
- **Hint.** For `@`, the escape; for a link, to check the id.

```tern {.live expect="ref.dangling"}
Thanks to @alice for the review.
```

The engine reports `ref.dangling` (warning) at 1:11:

- **Message:** `no id in this note has this name, so the reference stays text`
- **Hint:** `if it is not a reference, write \@alice`

**Fix.** Escape a mention:

```tern {.live}
Thanks to \@alice for the review.
```

A fragment link:

```tern {.live expect="ref.dangling"}
See [the proof](#proof).
```

The engine reports `ref.dangling` (warning) at 1:5:

- **Message:** `the link points to #proof, which names no id in this note`
- **Hint:** `check the id, or give the target that id`

**Related.** [`ref.unreferenceable`](#ref-unreferenceable), [`id.duplicate`](#id-duplicate).

### `ref.unreferenceable` {#ref-unreferenceable}

**Warning.** An id that `@` cannot reach.

- **Trigger.** An `id=` value that is a valid HTML id but not a Tern identifier: it starts with a digit, or holds `:` or `.`, as `id=2024` or `id=a.b`. A `#2024` is [`attr.malformed`](#attr-malformed) instead.
- **Position.** The first letter of `id=`.
- **Content.** The id is kept. A fragment link, `[text](#2024)`, still reaches it.

```tern {.live expect="ref.unreferenceable"}
[The plan]{id=2024}
```

The engine reports `ref.unreferenceable` (warning) at 1:12:

- **Message:** `the id "2024" is kept, but @ cannot reach it: a referenceable id starts with a letter or _ and holds no ":" or "."`
- **Hint:** `write it like {#plan-2024}`

**Fix.** Start the id with a letter:

```tern {.live}
[The plan]{#plan-2024}, see @plan-2024.
```

**Related.** [`id.invalid`](#id-invalid), [`ref.dangling`](#ref-dangling).

## Runtime {#runtime}

The browser reports these while it renders a note, after parsing. A live example cannot produce them, so their examples below are plain source. All six are errors. Each appears in the console, in the panel when it shows, and in `tern.diagnostics`, and each is passed to `tern.on('diagnostic', fn)` ([the lifecycle](api.html#lifecycle)).

### `math.error` {#math-error}

**Error.** KaTeX cannot typeset a formula.

- **Trigger.** KaTeX rejects the TeX of an inline or display formula, or of a `:::macros` block. Tern passes TeX to KaTeX unchanged, so this is a TeX error, not a Tern one.
- **Position.** The formula's start, from its element's `data-pos`: the `$` of inline math, the line of a display block's opening `$$`, or a `:::macros` block's opener.
- **Content.** The formula keeps its TeX as text. Its element gets the class `t-error` and a `title` holding KaTeX's message. Other formulas are unaffected.
- **When.** As formulas are typeset, which can be after the console group: a formula in a closed `
` is typeset when it opens.

```html

Bad $\frac{a}$ and good $x^2$.
```

The panel shows, at `line 1:5 (file line 2)`:

- **Message:** `KaTeX cannot typeset this formula: KaTeX parse error: Unexpected end of input in a macro argument, expected '}' at end of input: \frac{a}`
- **Hint:** `the formula is shown as written; fix its TeX`

A `:::macros` block that does not parse gives the message `the :::macros block does not parse: ` followed by KaTeX's message, and the hint `fix the TeX of the definitions`.

**Fix.** Correct the TeX: `$\frac{a}{b}$`. `tern build --katex` reports the same failures as warnings, with the code `math.error`, and leaves those formulas to tern.js ([building](publishing.html#build)).

**Related.** [`katex.unavailable`](#katex-unavailable), [`math.opener-tail`](#math-opener-tail).

### `addon.failed` {#addon-failed}

**Error.** An add-on did not load, or failed while it ran.

- **Trigger.**
  - **In the browser:**
    - a script or stylesheet listed in `data-use` fails to load. The note waits for every add-on to load or fail, then renders without the ones that failed. On a page written by `tern build`, only script add-ons are reported;
    - a script add-on throws while it runs;
    - a transform registered with `tern.transform(name, fn)` throws. The engine reports this one, so `tern.check` and the command line do too.
  - **On the command line and in the language server,** which run a note's script add-ons under node to learn its vocabulary (every `data-use` entry that is not a `.css` file):
    - an add-on file that cannot be read, or is a directory;
    - one that does not parse as a classic script, which is how tern.js runs an add-on;
    - one that throws;
    - a transform it registers that throws.

    A remote add-on is [`addon.remote`](#addon-remote) instead.
- **Position.** The `tern.js` line: line 0 in the browser, shown as `the tern.js line (file line 1)`; the file line of the tag, column 1, on the command line.
- **Content.**
  - An add-on that did not load: the note renders without it, so its names get the core output, with no label, counter or behaviour.
  - An add-on that threw: the note renders with what the add-on registered before the error.
  - A transform that threw: it is skipped, and the note renders without it.

```html

Hello.
```

The panel shows:

- **Message:** `the add-on missing.js did not load; the note renders without it`
- **Hint:** `check the path in data-use`

An add-on that throws while it runs, here `vocab.js` calling a function that does not exist:

- **Message:** `the add-on vocab.js threw while it ran: undefinedFn is not defined; the note renders with what it registered before the error`
- **Hint:** `fix the add-on; the browser console shows where it threw`

From a page opened as a `file:` URL, a browser may give only `Script error.` as the error's text; the console shows the real one.

A transform that throws, registered as `tern.transform('boom', fn)`:

- **Message:** `the transform "boom" threw: bad; the note renders without it`
- **Hint:** `` fix the function given to tern.transform("boom", …) ``

`tern check` prints the reason, with no hint:

```sh
$ tern check note.html
note.html:1:1: error addon.failed: the add-on missing.js did not load: cannot read /home/me/notes/missing.js
note.html:1:1: error addon.failed: the add-on bad.js did not load: it does not parse as a classic script, which is how tern.js runs an add-on: Unexpected identifier 'is'
note.html:1:1: error addon.failed: the add-on throws.js did not load: it threw: undefinedFn is not defined
note.html:1:1: error addon.failed: the transform "boom" of the add-on tx.js threw: bad
```

A directory reads `/home/me/notes/dir.js is a directory`. `tern build` prints these as `tern build:` warnings, since the page itself is still written.

**Fix.** Check the path in `data-use`. A relative path resolves from the note, as any URL in it does ([add-ons](schema.html#addons)). For an add-on or a transform that throws, fix its code.

**Related.** [`addon.remote`](#addon-remote), [`head.script`](#head-script), [`katex.unavailable`](#katex-unavailable).

### `katex.unavailable` {#katex-unavailable}

**Error.** KaTeX did not load.

- **Trigger.** KaTeX's script or stylesheet fails to load from its base: the pinned CDN by default, or the URL in `data-katex`. It is reported once, and only when the note has math.
- **Position.** The `tern.js` line (line 0).
- **Content.** Every formula is shown as its TeX source.

```html

Math $x^2$ here.
```

When `vendor/katex` does not hold KaTeX, the panel shows:

## Command line and editors {#tools-codes}

### `head.script` {#head-script}

**Info or warning.** A head script was not run under node.

- **Trigger.** The command line and the language server run the classic scripts in the head, before the `tern.js` line, to learn the vocabulary they declare in `window.TERN.schema` ([`window.TERN`](schema.html#window-tern)). Inline scripts and local files run; `async`, `defer` and module scripts are left out. This fires for a head script they could not run:
  - **info:** a remote script, which they never load;
  - **warning:** a local script that cannot be read, or a script that throws.

  `tern check` and the language server report it. `tern build` prints the warnings among its own `tern build:` lines. The browser runs head scripts itself, so it never reports this code.
- **Position.** The script's `



:::theorem
…
:::
```

When `vocab.js` is missing, `tern check` prints:

```sh
$ tern check note.html
note.html:2:1: info head.script: the head script https://example.com/vocab.js is not run under node, so vocabulary it declares in window.TERN.schema is unknown here
note.html:3:1: warning head.script: the head script vocab.js cannot be read (/home/me/notes/vocab.js)
```

A script that throws reads `the head script vocab.js threw under node: ` and the error, then `; vocabulary it declares may be missing`. An inline script is named `inline script on line N`.

**Fix.** Keep the vocabulary in a local file, or inline in the head, so that the tools can read it. A remote script stays an info: the tools work without its names, and the page has them.

**Related.** [`addon.remote`](#addon-remote), [`addon.failed`](#addon-failed).

### `addon.remote` {#addon-remote}

**Info.** A remote add-on was not loaded under node.

- **Trigger.** A `data-use` entry with a remote URL, such as `https://…`. The command line and the language server load nothing from the network, so they do not learn the names the add-on declares. The browser loads it as usual, so it never reports this code.
- **Position.** The `tern.js` line, as a file position: the file line of the tag, column 1. It has no note position and no hint.
- **Content.** The note is checked without the add-on's vocabulary, so its names get the core output there. The page in the browser is not affected. Being an info, it does not make `tern check` fail; `tern build` prints it as a `tern build:` warning, since the page it writes uses those names without their schema.

```html

Hello.
```

```sh
$ tern check note.html
note.html:1:1: info addon.remote: the add-on https://example.com/vocab.js is not loaded under node; names it declares are unknown to tern check
tern check: 1 note: 0 errors, 0 warnings, 1 info
```

**Fix.** Nothing is wrong with the page. To check the note with its vocabulary, keep a local copy of the add-on and list that in `data-use`.

**Related.** [`addon.failed`](#addon-failed), [`head.script`](#head-script).
