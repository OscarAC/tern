:::meta description: The tern object in node and in the browser: parse, transform, emit, toHTML, check, visit, outline, the schema registry, the runtime API and its events, tern.config, the lifecycle, and the AST with its data.tern fields. ::: ::site-nav # JavaScript API {#top} ::toc Everything Tern does is on one object, `tern`. In a browser it is `window.tern`; under node it is what `require('./tern.js')` returns. It has two halves: - **The engine** turns a note's source into an AST, computes its semantics and writes HTML. It is pure: no DOM, no I/O, the same output in node and in every browser. - **The runtime** renders a note in the page, runs DOM behaviours and fires events. It exists only in a browser. Under node its members are present but do nothing. This page is the reference for both, for the order in which the runtime does things, and for the AST the engine produces. It never rejects. Unlike `tern.on('ready')`, it works whenever you await it, before or after the event. ```js await tern.ready; document.querySelectorAll('main.tern .t-math .katex').length; // the typeset formulas ``` It never settles under node, nor on a page where the runtime did not start ([When nothing starts](#no-start)). ### `tern.diagnostics` {#diagnostics} The page's diagnostics, in one array that stays the same object for the life of the page: hold a reference and it stays current. - **At mount** it holds, sorted by position: - the runtime diagnostics found before the mount, at line 0, which therefore come first: [`doc.quirks`](diagnostics.html#doc-quirks), and [`addon.failed`](diagnostics.html#addon-failed) for an add-on that did not load or threw while it ran; - the note's parse and transform diagnostics, as [`tern.check`](#check) returns them, including `addon.failed` for a registered transform that threw. - **Later** runtime diagnostics are appended as they happen: [`script.document-write`](diagnostics.html#script-document-write) and [`script.domcontentloaded`](diagnostics.html#script-domcontentloaded) while the note's scripts run, then [`math.error`](diagnostics.html#math-error) and [`katex.unavailable`](diagnostics.html#katex-unavailable) while math is typeset. Each diagnostic the runtime reports itself, early or late, also fires the [`diagnostic`](#on) event; those of the parse and the transforms do not. - **`tern.render(main, source)`** replaces the contents with the new note's diagnostics, keeping the line-0 ones. - **On a built page** it holds the build's diagnostics, read from the page, then an `addon.failed` for each add-on script that failed to load or threw while it ran. Each entry has the [shape of a diagnostic](#check). Where both set a key, the attribute wins. ```html ``` On that page, once tern.js has started: ```js tern.config; // → { use: { theorems: { labels: 'de' }, theme: { dark: '' } }, // katex: { macros: { '\\R': '\\mathbb{R}' }, base: '/vendor/katex' }, // lang: 'en', nonce: 'abc', diagnostics: false, quiet: false } ``` - **When.** `tern.config` is filled once, when tern.js starts. So `window.TERN` must be set by a script in the head, before the tern.js line; setting it later does nothing. - **What is copied.** Every key of `window.TERN` is copied into `tern.config`, including keys Tern does not use. An add-on can read its own settings from there. - **Booleans.** For `data-diagnostics` and `data-quiet`, the values `false`, `0`, `off` and `no` (in any case) mean false; any other value, or none, means true. Its value is a list of URLs, separated by spaces, resolved against the page. An entry ending in `.css` (before its query) is a stylesheet, linked in its place in the [cascade](#style); any other is a script. Scripts are fetched in parallel and run in the order listed, and the note mounts only once every entry has loaded or failed. **KaTeX options.** Every key of `katex` except `base`, `displayMode` and `throwOnError` is passed to KaTeX: `macros`, `trust`, `strict`, `output`, `leqno` and the rest. `throwOnError` is always true, so that a bad formula is reported as `math.error` and keeps its TeX. `macros` is copied into one table that every formula shares; the `:::macros` blocks of the note are defined into it first. Two other attributes belong to the tag but not to `tern.config`. `data-built` marks a page written by `tern build`, with the value `math` when the build left formulas to typeset ([A built page](#built-page)). `src` must name a file called `tern.js` for editors and the command line to [detect the note](tools.html#detection).
