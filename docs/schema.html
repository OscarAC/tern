:::meta description: How to give Tern's element names meaning, look and behaviour: the schema and every schema field, window.TERN.schema, add-ons, tern.define, custom transforms, styling, and labels in other languages. ::: ::site-nav # Vocabulary and behaviour {#top} ::toc Tern's core knows how a name is *written*, as in `:::theorem`, `::toc` or `:kbd[Ctrl]`, but not what it *means*. A **schema** gives names their meaning: the element, a label such as "Theorem 2", a counter, how a reference reads, a title slot, an end mark, a table of contents. The schema's `css` and `dom` fields, `tern.style` and `tern.define` give them a look and a behaviour. This page covers all of it, from a note that declares three names in its head to an add-on shared by a hundred notes. The live examples run with **no schema** unless they say `schema=demo`. The demo schema is the small vocabulary listed at the [end of this page](#demo-schema). ## Why names need a schema {#why} The core gives a name no meaning. `:::theorem` is `div.t-block.theorem` until a schema says otherwise: no label, no number, and a reference to it reads its title. ```tern {.live} :::theorem[Rank–nullity]{#rn} $\dim V = \dim \ker T + \dim \operatorname{im} T$. ::: See @rn. ``` The same note with the demo schema, which declares `theorem`: ```tern {.live schema=demo} :::theorem[Rank–nullity]{#rn} $\dim V = \dim \ker T + \dim \operatorname{im} T$. ::: See @rn. ``` The difference is one entry: ```js theorem: { tag: 'section', counter: 'theorem', label: 'Theorem', ref: '{label} {n}' } ``` **Why the core declares nothing.** Every subject needs its own names: a lecture has theorems, a lab notebook has protocols, a cookbook has steps. Labels differ from one language to the next. And a note must render from one script line, without a standard library to keep in step with it. So a note, or an add-on it loads, declares exactly the names it uses. A name without an entry still renders. It keeps its class and its `data-t`, so CSS and behaviours can find it, and it becomes an element on its own when the name is one: - an allowlisted element: `:::aside` is an `
`; - a custom element: `:::tide-panel` is a ``. [Elements and output](elements.html#names) has the whole resolution. :::table[What a schema entry adds]{#tbl-adds} | | Without an entry | With an entry | |---|---|---| | Element | `div` or `span`, or the name itself when it is an element | `tag` | | Classes and attributes | `t-block`, the name, the author's | `class`, `attrs` | | Label | none | `label` | | Number | none | `counter` | | Reference text | the title, else the id | the label and number, through `ref` | | Title element | written titles only | `title`, `titleDefault`, and a slot for the label | | End mark | none | `end` | | Body | blocks, or verbatim with `{raw}` | `body` | | Generated content | none | `transform: 'toc'` | | Look | the base stylesheet | `css` | | Behaviour | `tern.define` only | `dom` | ::: **Where vocabulary comes from.** 1. **The note's own head:** `window.TERN.schema`, in a script before the tern.js line ([below](#window-tern)). Best for a note that stands alone. 2. **An add-on** listed in `data-use`, which calls `tern.block`, `tern.leaf` and `tern.inline` ([Add-ons](#addons)). Best for vocabulary shared by several notes. 3. **Node**, for scripts that call the engine: the same three functions, or a `schema` option on each call ([JavaScript API](api.html#registry)). When a note and an add-on declare the same name, the note's entry wins. ## The schema {#schema} ### The registry {#the-registry} A schema is plain data: an object with three levels, each mapping a name to an entry. ```js { block: { theorem: { tag: 'section', counter: 'theorem', label: 'Theorem' } }, leaf: { toc: { tag: 'nav', transform: 'toc' } }, inline: { key: { tag: 'kbd' } }, } ``` In the browser this object is `tern.schema`, the registry. Three functions write it: :::syntax ```js tern.block(name, spec) // :::name … ::: tern.leaf(name, spec) // ::name[…]{…} tern.inline(name, spec) // :name[…]{…} ``` ::: - **The entry.** Each function stores a shallow copy of `spec` and returns it. Changing your `spec` object afterwards changes nothing; changing the stored entry does: `tern.schema.block.note.label = 'Hinweis'`. - **Again.** Registering a name a second time replaces its entry whole. - **Refused.** They throw a `TypeError`, and register nothing, when: - the name is not a NAME: a letter, then letters, marks, digits, `_` or `-`; - the name is reserved: `base body head html link main meta noscript script style template title`, `tern`, any `t-…` name, and `end`; - a block name is one of the core containers `meta`, `macros`, `script`, `style` or `html`; - `spec` is not an object. - **When.** The registry is read each time a note is rendered. Declare entries in an add-on or in `window.TERN.schema`: both are applied before the note is mounted. A ` ::toc ## The theorem :::theorem[Rank–nullity]{#rn} $\dim V = \dim \ker T + \dim \operatorname{im} T$. ::: :::proof Extend a basis of $\ker T$ to a basis of $V$. ::: ## Using it By @rn, … Press :key[Ctrl]. ``` The toc is a `nav` with two entries, the theorem a `section` labelled "Theorem 1", the proof ends with ∎, `@rn` reads "Theorem 1", and `:key[Ctrl]` is a ``. :::note The examples in this section are source, not live. A live example renders with the engine alone, and `tern.toHTML(source, {head})` reads the head only for what `:::meta` and the labels need: its ``, the `lang` and `dir` of `<html>`, and its `<meta name>` tags. It runs no script. Running the head's scripts is the job of the browser runtime and the command line. Under node, pass the vocabulary as the `schema` option instead. ::: **The rules.** - **Shape.** `window.TERN.schema` holds `block`, `leaf` and `inline`, each optional, with entries as for `tern.block`. Function fields (`label`, `dom`) and `css` work as in an add-on. - **Where.** In a classic `<script>` before the tern.js line: inline, or a `src` file of your own (`<script src="vocabulary.js">`). tern.js reads `window.TERN` when it starts. The command line runs only classic head scripts, not `async`, `defer` or module ones. - **When.** At mount, after every add-on has registered its entries. Each entry goes through `tern.block`, `tern.leaf` or `tern.inline`. - **Precedence.** So the note's entry replaces an add-on's entry for the same name, **whole**: the fields are not merged. An add-on's `dom` for that name is gone, unless the note's entry has one too. - **A bad entry** (a reserved name, a value that is not an object) is skipped with a warning in the console; the others apply. - **The levels and `strict`** are read: `strict: true` turns on [strict names](#strict), and `strict: false` turns off an add-on's. `window.TERN` carries other settings too, such as `lang`, `use` and `katex` ([Configuration](api.html#config)). - **Built pages.** `tern build` applies the vocabulary when it writes the HTML. tern.js applies it again when the built page starts, for the behaviours and for `tern.render`. **Under node.** `tern check`, `tern parse`, `tern build` and the language server run the head's scripts in a sandbox, in document order, before the add-ons. Then `window.TERN.schema` goes on top, as in the browser. - An inline script, or a `src` file on disk, runs. - A remote `src` is not run: `head.script` (info). - A missing file, or a script that throws, gives `head.script` (warning). **Changing one field of an add-on's entry.** A note's own entry replaces the add-on's whole. To change one field and keep the rest, list a small add-on of your own after it in `data-use`, and assign into the registry: ```js // tweaks.js, listed after the add-on: data-use="callout.js tweaks.js" tern.schema.block.note.label = 'Hinweis'; ``` **Diagnostics:** [`head.script`](diagnostics.html#head-script), from the command line and the language server only. ## Add-ons {#addons} An add-on is a script or a stylesheet listed in `data-use` on the tern.js tag: ```html <!doctype html><meta charset="utf-8"><script src="tern.js" data-use="lib/callout.js lib/theme.css"></script> ``` ### Listing add-ons {#data-use} - **The list** is space-separated. Each entry is a URL, relative to the page like any `src`. - **Stylesheets and scripts.** An entry whose path ends in `.css` is a stylesheet; anything else is a script. - **Order matters.** Scripts run in the order listed, so a later add-on sees an earlier one's entries and can change them. Stylesheets cascade in the order listed: a theme listed after an add-on wins at equal specificity. - **Under node**, the command line reads the entries the same way: every entry that does not end in `.css` is run as a classic script, `.mjs` or no extension included. One that does not parse as a classic script, or names a directory, is `addon.failed`. ### Options in the query string {#use-options} An add-on takes options from its URL's query string, in `tern.config.use`: ```html <script src="tern.js" data-use="lib/callout.min.js?collapse=all&accent=teal"></script> ``` ```js tern.config.use.callout // {collapse: 'all', accent: 'teal'} ``` - **The key** is the file name without its directory, `.min`, and `.js`, `.mjs` or `.css`: `lib/callout.min.js` is `callout`. - **Every entry** gets an object, empty when there is no query. - **Values** are strings. A key without `=` gets `''`. - **Defaults.** `window.TERN.use = {callout: {collapse: 'none'}}` gives defaults; the query string wins key by key. - **`&`** is the strict HTML spelling of `&` in an attribute; both work. - **Under node, `tern.config.use` is empty.** Read options only for behaviour and style, never for vocabulary, or `tern check` and `tern build` would not see what the browser sees ([Under node](#addons-under-node)). ### How they load {#addon-loading} 1. When tern.js starts, it adds a preload for every script add-on, then appends them all at once: they **download in parallel** and **run in the order listed**. Stylesheets are added as links, in order. 2. The note is rendered once the document is parsed and **every add-on has loaded or failed**. There is no timeout. 3. So an add-on runs **before the mount**. `window.tern` exists; `window.TERN.schema` is not applied yet; the note's elements do not exist yet. An add-on therefore registers things, for the runtime to apply when the note is rendered: - vocabulary: `tern.block`, `tern.leaf`, `tern.inline`; - behaviours: `tern.define`; - listeners: `tern.on`; - transforms: `tern.transform`; - styles: `tern.style`. It does not look for the note's elements itself: they are not there yet. ### When an add-on fails {#addon-failed} **`addon.failed`** is an error at the tern.js line. The note always renders. It is reported when: - a script or stylesheet does not load (a wrong path, a network error): the note renders without it; - a script throws while it runs: the note renders with what the add-on registered before the error, and the browser's console shows where it threw; - a transform the add-on registered throws when it runs: that transform is skipped ([Custom transforms](#transforms)). The command line and the language server report the same cases, and a few of their own: - a missing file, or a directory; - a script that does not parse as a classic script; - a script that uses what the [node shim](#addons-under-node) does not provide. **A remote add-on** (`https://…`) is not loaded under node. That is **`addon.remote`**, an info at the tern.js line: names it declares are unknown to `tern check`, which does not fail because of it. `tern build` warns about it: the page it writes uses those names without their schema entries. **Diagnostics:** [`addon.failed`](diagnostics.html#addon-failed), [`addon.remote`](diagnostics.html#addon-remote). ## Writing an add-on {#writing-an-addon} ### A complete add-on {#callout-addon} This add-on declares three callouts, `note`, `tip` and `warning`, with labels in three languages, a stylesheet, and a behaviour that folds a callout away. ```js [callout.js, a complete add-on]{#lst-callout} // callout.js: callouts for Tern notes, in English, German and French. // <script src="tern.js" data-use="callout.js"></script> // <script src="tern.js" data-use="callout.js?collapse=all"></script> (function () { 'use strict'; const tern = window.tern; // 1. Vocabulary: three containers with a label in three languages. const labels = { note: { en: 'Note', de: 'Hinweis', fr: 'Remarque' }, tip: { en: 'Tip', de: 'Tipp', fr: 'Astuce' }, warning: { en: 'Warning', de: 'Warnung', fr: 'Attention' }, }; for (const name of Object.keys(labels)) { tern.block(name, { tag: 'aside', class: 'callout', attrs: { role: 'note' }, label: labels[name], dom: collapsible, }); } // 2. Look: keyed on the classes, never on the tag. tern.style(` .tern .callout { border-inline-start: 4px solid var(--callout, var(--t-link)); background: var(--t-soft); padding: .6rem 1rem; border-radius: 6px; } .tern .callout.tip { --callout: #2f8a46; } .tern .callout.warning { --callout: var(--t-warn); } .callout-toggle { margin-inline-start: .5rem; font: inherit; cursor: pointer; } @media print { .callout-toggle { display: none; } } `); // 3. Behaviour: a callout with data-collapse, or every callout with // ?collapse=all, gets a button that folds its body away. const options = tern.config.use.callout || {}; // empty under node function collapsible(el) { const title = el.querySelector(':scope > .t-title'); if (!title || !(options.collapse === 'all' || el.hasAttribute('data-collapse'))) return; const button = document.createElement('button'); button.type = 'button'; button.className = 'callout-toggle'; button.setAttribute('aria-expanded', 'true'); button.textContent = 'Hide'; button.addEventListener('click', () => { const open = button.getAttribute('aria-expanded') === 'true'; button.setAttribute('aria-expanded', String(!open)); button.textContent = open ? 'Show' : 'Hide'; for (const child of el.children) if (child !== title) child.hidden = open; }); title.append(button); } })(); ``` A note that uses it: ```html <!doctype html><html lang="de"><meta charset="utf-8"><script src="tern.js" data-use="callout.js"></script> :::warning[Strom]{#w data-collapse} Erst den Stecker ziehen. ::: ``` The engine writes this (as `tern build` shows it, without positions), and the behaviour then adds the button to the title: ```html <aside id="w" class="t-block warning callout" data-t="warning" role="note" data-collapse><div class="t-title"><span class="t-label">Warnung</span> Strom</div><p>Erst den Stecker ziehen.</p> </aside> ``` What each part does: - **The wrapper** keeps the add-on's names out of the page's globals, and reads `window.tern`, which tern.js defined before any add-on runs. - **The vocabulary.** The label map picks "Warnung" from `<html lang="de">` ([Labels in other languages](#languages)). `class` and `attrs` give every callout the class `callout` and `role="note"`. - **The look.** `tern.style` puts the rules at this add-on's place in the cascade and adds the page's nonce. Most of the rules use tern's custom properties, so they follow dark mode ([Styling](#styling)). - **The behaviour** reads a per-element option from a `data-*` attribute (`{data-collapse}`), and a per-note option from the query string. ### Guidelines {#addon-guidelines} - **Register everything while the script runs.** The mount comes after; nothing registered later applies to the note until the next render. - **Key CSS and behaviours on the class or `data-t`, never on the tag.** An author can change the tag with `{tag=…}`. - **Use `tern.style`** rather than adding your own `<style>`: it keeps the cascade order of `data-use`, and the nonce of a strict CSP ([CSP](publishing.html#csp)). - **Prefer `data-*` attributes** for options on one element. Any key is written to the element as given, but most HTML elements accept only `data-*` and their own attributes. - **Guard the options:** `tern.config.use.NAME || {}`. Under node the object is missing. - **Never derive vocabulary from options.** Labels, tags and counters must be the same under node, where `tern.config.use` is empty, as in the browser. Use a label map for languages. - **Walk the tree yourself in a transform.** Under node, `tern` is a shim without `tern.visit` (next section), so a transform that calls it fails there. - **Stay within the browser** at load time: the command line runs the add-on with stand-ins for the DOM (next section). ### Under node: the command line and the language server {#addons-under-node} `tern check`, `tern parse`, `tern build` and `tern lsp` need a note's vocabulary, so they load it in a node `vm` sandbox, in this order: 1. the head's classic scripts before the tern.js tag ([Declaring vocabulary in a single file](#window-tern)); 2. the `data-use` script add-ons, with `window.tern` set to a **shim**; 3. `window.TERN.schema`, on top. :::table[The window.tern shim]{#tbl-shim} | Part | Under node | |---|---| | `tern.block`, `tern.leaf`, `tern.inline` | work: they store the spec as given, without the name checks | | `tern.schema` | the registry being built: `tern.schema.strict = true` and edits to entries work | | function fields (`label`, `dom`) | kept; a label function runs | | `tern.transform` | works: the transform runs in `tern check`, `tern parse --transformed`, `tern build` and the language server | | `tern.version` | the engine's version | | `tern.define`, `undefine`, `on`, `style` | accepted and ignored | | `tern.render` | resolves to `[]` | | `tern.ready` | a promise that never settles | | `tern.diagnostics` | an empty array | | `tern.config` | `{use: {}, katex: {}}`: no query options | | everything else on `tern` (`parse`, `toHTML`, `visit` …) | absent: calling it throws, so the add-on, or the transform that called it, is `addon.failed` | ::: - **Browser globals** (`document`, `customElements`, `HTMLElement`, `fetch`, `setTimeout` …) are stand-ins that accept anything and do nothing. So `customElements.define(…)` or `class X extends HTMLElement` does not stop the add-on before its `tern.block` calls. - **`window`**, `self` and `globalThis` are the sandbox. Its `console` writes to stderr. - **Each script** gets 2 seconds. - **Files.** Only local files load: a relative URL from the note's directory, a root-relative one (`/lib/x.js`) from the note's directory or the nearest ancestor that has it. A remote add-on is not loaded: `addon.remote` ([When an add-on fails](#addon-failed)). What follows from the shim: - **Vocabulary is identical** under node and in the browser, if the add-on declares it without reading options or the DOM. - **Transforms run** under node as in the browser: `tern check` reports their diagnostics, and `tern build` writes their changes into the page. A transform that throws is skipped and reported as `addon.failed`. - **Behaviours and styles** do not run under node. A page written by `tern build` loads the add-on in the browser, where they run. **The language server** uses the same loader, cached per note directory, tern.js tag and head scripts. A change to an add-on file takes effect at the note's next edit. Completion lists the schema's names; hover on a name shows its element and whether the schema, the allowlist or neither gave it ([The language server](tools.html#lsp)). ## Behaviours {#behaviours} A behaviour is a function the runtime calls for each element of a name, after the note is in the page: to add a button, start a widget, read the element's data. ### `tern.define` {#tern-define} :::syntax ```js const undo = tern.define(name, fn) // fn(el), with this === el tern.undefine(name) ``` ::: ```js tern.define('countdown', (el) => { const days = Math.ceil((new Date(el.dataset.to) - Date.now()) / 864e5); el.textContent = `${el.dataset.label}: ${days} days`; }); ``` - **Keyed on `data-t`.** `fn` runs for every element whose `data-t` is `name`: containers, leaves and inline elements, with or without a schema entry, and every fence (`data-t="code"`). A bare span `[x]{…}` has no `data-t`. - **Once per element** and function. Elements are remembered, so `tern.render()` never runs a function twice on one element. - **Document order**, element by element. For each element: its schema `dom`, then each `define` function for its name, in registration order. - **Before math.** Formulas are still TeX, in `data-tex`, when behaviours run. See [Behaviours that need typeset math](#pattern-math). - **Additive.** Several functions per name all run. - **`undo()`** removes that one function, for elements met afterwards; what it did to earlier elements stays. - **`tern.undefine(name)`** removes every function `define` registered for the name. A schema `dom` stays. - **Late.** A function defined after the behaviours ran, in a `ready` listener for example, runs at once on the elements already in the page. - **Errors** are caught and logged (`tern: the "name" behaviour failed`); the other behaviours go on. - **Arguments.** A name that is not a non-empty string, or an `fn` that is not a function, throws a `TypeError`. - **Where.** In an add-on, or in a `<script>` in the note: note scripts run after the mount and before the behaviours. - **Under node** `define` is accepted and never runs. What a behaviour can find: a leaf and a fence carry `data-t`, a bare span does not. ````tern {.live} ::countdown{data-to=2026-12-31 data-label="New year"} ```js console.log('a fence'); ``` A [bare span]{.aside}. ```` ### A `dom` function in a schema entry {#dom-function} A schema entry's `dom` is a behaviour declared with the vocabulary: same signature, same rules. - **It runs first** on its element, before the `define` functions. - **One per element.** The runtime looks for a `dom` level by level and runs the first it finds. For an element with the class `t-block` (a container, or a titled fence) the order is block, leaf, inline; for any other, leaf, inline, block. So both an untitled fence (`pre`) and a titled one (`figure.t-block`) find `block.code`'s `dom`, unless a leaf or inline entry named `code` has one. - **`window.TERN.schema`** may hold `dom` functions too. - **`tern.undefine`** does not remove it. ### Events {#events} :::syntax ```js const off = tern.on(event, fn) ``` ::: :::table[Events]{#tbl-events} | Event | When | `fn` receives | |---|---|---| | `render` | after the behaviours, before any formula is typeset | the root: `main.tern`, or the element given to `tern.render` | | `math` | after the formulas in view are typeset; again when a closed `<details>` opens and its formulas are typeset | the root, or that `<details>` | | `ready` | once, after the first `render` and `math` and the scroll to the URL's fragment | `main.tern` | | `diagnostic` | for each runtime diagnostic reported after you subscribe: `addon.failed`, `math.error`, `katex.unavailable`, `script.document-write`, `script.domcontentloaded` | the diagnostic object | ::: - `on` returns a function that unsubscribes `fn`. - Any other event name throws a `TypeError`. - `render` and `math` fire again at every `tern.render`. `ready` fires once: a listener added after it never runs, so use the promise `tern.ready` instead ([`tern.ready`](api.html#ready)). - An error in a listener is caught and logged. - Under node nothing fires. [The runtime lifecycle](api.html#lifecycle) shows where each event falls. ### Patterns {#patterns} #### An interactive element {#pattern-interactive} A spoiler: an inline element that is a real button, hidden until pressed. The schema gives the element, its attributes, its look and its behaviour. ```html <script> window.TERN = {schema: {inline: {hide: { tag: 'button', attrs: {type: 'button', 'aria-pressed': 'false'}, css: '.tern .hide[aria-pressed="false"] { color: transparent; background: var(--t-fg); }', dom(el) { el.addEventListener('click', () => { el.setAttribute('aria-pressed', el.getAttribute('aria-pressed') === 'true' ? 'false' : 'true'); }); }, }}}}; </script> ``` `The answer is :hide[42].` renders as `<button class="hide" data-t="hide" type="button" aria-pressed="false">42</button>`. Because it is a `<button>`, it is focusable and works from the keyboard with no extra code. #### Reading `data-*` attributes and raw bodies {#pattern-data} A behaviour reads its options from the element. Attributes written in braces arrive as written, so `el.dataset` holds them: ```tern ::countdown{data-to=2026-12-31 data-label="New year"} ``` ```js tern.define('countdown', (el) => { const days = Math.ceil((new Date(el.dataset.to) - Date.now()) / 864e5); el.textContent = `${el.dataset.label}: ${days} days`; }); ``` For more than a few values, give the container a raw body (`{raw}`, or `body: 'raw'` in its entry). The behaviour reads it as `el.textContent`: ```tern :::chart{raw} month,rain Jan,62 Feb,48 ::: ``` ```js tern.define('chart', (el) => { const [head, ...rows] = el.textContent.trim().split('\n').map((line) => line.split(',')); // … draw the chart from head and rows, then replace el's content }); ``` No schema entry is needed: `::countdown` and `:::chart` already carry their `data-t`. #### Behaviours that need typeset math {#pattern-math} Behaviours always run before math. A behaviour that needs KaTeX's output listens for `math`: ```js tern.on('math', (root) => { for (const eq of root.querySelectorAll('.t-eq')) { eq.classList.toggle('wide', eq.scrollWidth > eq.clientWidth); } }); ``` - `math` fires on `main.tern` once the formulas in view are typeset. - Formulas inside a closed `<details>` wait until it opens; `math` then fires again with the `<details>` as `root`. So work inside `root`, and make the handler safe to run twice. - Before typesetting, every formula's TeX is in its `data-tex` attribute, which stays after typesetting too. To render new Tern content into a part of the page, as a live preview does, use `tern.render(root, source)`: it runs the behaviours on the new elements and typesets their math ([`tern.render`](api.html#render)). ## Custom transforms {#transforms} A transform computes something from the whole note before it is written: a glossary, an index, a count, a check. It works on the AST, so its result is in the HTML from the start, in the browser and in `tern.toHTML`. :::syntax ```js const remove = tern.transform(name, fn, {before: 'refs'}) // or {after: 'numbering'} // fn(ast, ctx), with ctx = {schema, opts, lang, report} ``` ::: - **`name`**: a non-empty string that is not a built-in transform's name. Registering a name again moves it and replaces its function. - **Where it runs:** `{before: 'x'}` or `{after: 'x'}`, where `x` is any transform already registered. Without either, it runs last. An unknown `x` throws. - **`remove()`** takes it out. A `remove` from an earlier registration of the same name does nothing. - **`fn(ast, ctx)`** changes `ast` in place. Its return value is ignored. - **A transform that throws** is skipped, and the note renders without it. It is reported as `addon.failed`, an error at line 0: "the transform "NAME" threw: MESSAGE". - **Once per tree.** A tree is transformed once; transforming it again returns it unchanged. :::table[The built-in transforms, in order]{#tbl-transforms} | Transform | Does | So a transform placed after it sees | |---|---|---| | `figures` | turns an image with an id into a `figure` container | implicit figures as containers | | `tables` | merges a `table` container with its pipe table | merged tables | | `attributes` | resolves elements, title slots, schema `class` and `attrs`, reserved keys | `data.tern.tag`, `data.tern.slot` | | `footnotes` | numbers footnotes, `fn-`/`fnref-` ids | footnote numbers | | `ids` | the id registry, heading slugs, invalid and duplicate ids | every heading's id | | `numbering` | counters, labels, equation numbers | `data.tern.number`, `data.tern.text` | | `refs` | fills references, checks fragment links | reference text | | `toc` | fills `toc` leaves | tables of contents | | `meta` | the title fallback | `data.tern.meta.title` | ::: So a transform that adds ids or headings runs **before `ids`**: then references to its ids resolve, and its headings get slugs and enter the table of contents. One that reads numbers runs **after `numbering`**. [The transformed AST](api.html#transformed-ast) lists every field the built-in transforms write. **`ctx`:** - `ctx.schema`: the registry in use; - `ctx.opts`: the options of the call (`head`, `lang` …); - `ctx.lang`: the label language ([Labels in other languages](#languages)); - `ctx.report(code, at, message, hint, severity)` adds a diagnostic. - `at` is a node (its position is used) or a position `{start, end}`; without one, line 1, column 1. - `severity` is `'error'`, `'warning'` (the default) or `'info'`. A code of Tern's own keeps its own severity, so name yours after your add-on: `glossary.empty`. - Your diagnostics reach `tern.check`, `tern.diagnostics`, the console and the panel like Tern's. ### A worked transform {#glossary} A glossary: `:term[…]` marks a term, and a `::glossary` leaf lists every term once, sorted, each linking to its first use. ```js [glossary.js, an add-on with a transform]{#lst-glossary} (function () { 'use strict'; const tern = window.tern; tern.inline('term', { tag: 'dfn' }); tern.leaf('glossary', { tag: 'nav' }); const walk = (node, fn) => { fn(node); if (node.children) for (const child of node.children) walk(child, fn); }; const text = (nodes) => nodes.map((n) => n.value || (n.children ? text(n.children) : '')).join(''); tern.transform('glossary', (ast, ctx) => { const terms = new Map(); // term -> the id of its first use const lists = []; walk(ast, (node) => { if (node.type === 'leafDirective' && node.name === 'glossary') lists.push(node); if (node.type !== 'textDirective' || node.name !== 'term') return; const word = text(node.children).trim(); if (!word) return ctx.report('glossary.empty', node, 'this term is empty', 'write the term in the brackets: :term[kernel]'); if (terms.has(word)) return; const a = node.attributes || (node.attributes = {}); if (a.id === undefined) a.id = `term-${terms.size + 1}`; terms.set(word, a.id); }); if (terms.size && !lists.length) ctx.report('glossary.missing', null, 'the note has terms but no ::glossary', 'add ::glossary where the list goes', 'info'); const items = [...terms.keys()].sort((a, b) => a.localeCompare(b)).map((word) => ({ type: 'listItem', spread: false, checked: null, children: [{ type: 'paragraph', children: [{ type: 'link', url: `#${terms.get(word)}`, title: null, children: [{ type: 'text', value: word }] }] }], })); for (const leaf of lists) leaf.children = [{ type: 'list', ordered: false, start: null, spread: false, children: items }]; }, { before: 'ids' }); })(); ``` With it, `A :term[kernel] is a set; so is the :term[image].` followed by `::glossary` renders as: ```html <p>A <dfn id="term-1" class="term" data-t="term">kernel</dfn> is a set; so is the <dfn id="term-2" class="term" data-t="term">image</dfn>.</p> <nav class="glossary" data-t="glossary"><ul> <li><a href="#term-2">image</a></li> <li><a href="#term-1">kernel</a></li> </ul> </nav> ``` - It runs **before `ids`**, so the ids it gives the terms are registered: the links are checked like any fragment link, and `@term-1` would resolve. - It walks the tree with its own `walk`, not `tern.visit`, which the command line's shim does not have. So it runs in the browser, in `tern check` and in `tern build` alike. - The nodes it builds are mdast nodes ([Node types](api.html#node-types)); the emitter writes them like parsed ones. They have no positions, so they get no `data-pos`. - An empty `:term[]` gets `glossary.empty` (warning) at the term. ### When to use a transform {#when-transform} Use a transform when: - the result depends on the whole note (counts, indexes, cross-references); - it must be in the HTML before any script runs, with no flash of unfinished content; - it must be in `tern.toHTML`'s output. Use a behaviour when the work needs the page: events, measurement, a widget, data fetched at run time. Where transforms run: - **in the browser**, once per tree: at mount, and at each `tern.render(root, source)`; - **under the command line and the language server**, from an add-on: `tern check` reports their diagnostics, and `tern build` writes their changes into the page ([Under node](#addons-under-node)); - **under node, in your own script**: a transform registered with `require('./tern.js').transform(…)` runs in `toHTML`, `check` and `transform`. ## Styling {#styling} ### Classes and attributes {#classes} Every element Tern writes carries classes and attributes to key CSS on. `11pt` in print | | `--t-leading` | `1.6` | | the line height | | `--t-cols` | | | a grid's columns, set by Tern on each grid | ::: ### Overriding them {#overriding} Set the properties in your own CSS. A style in the head, before the tern.js line, is enough: ```html <!doctype html><meta charset="utf-8"><style> :root { --t-width: 48rem; --t-font: "Iowan Old Style", Georgia, serif; --t-link: #8a3ffc; } </style><script src="tern.js"></script> ``` **The cascade.** Tern's stylesheets form one group in the head, placed before the head's first stylesheet of your own, in this order: 1. KaTeX's stylesheet; 2. the base, `tern.css`; 3. each add-on in `data-use` order: a CSS add-on's link, or the `tern.style` sheets a script add-on adds; 4. other `tern.style` sheets: from `window.TERN.schema` entries, from note scripts. Your own head styles come after the group, and a `<style>` written in the note after that. So at equal specificity, **your CSS wins** over Tern's and over every add-on's. Ways to add your own CSS: - a `<style>` or `<link rel="stylesheet">` in the head, before the tern.js line; - a `<style>` block in the note, as raw HTML; - a CSS add-on: `data-use="theme.css"`, ordered among the add-ons; - `tern.style(css)` from a script; - a schema entry's `css`. ### `tern.style` {#style-api} :::syntax ```js tern.style(css) // adds a <style> to the head; returns it ``` ::: - **While an add-on runs,** the sheet goes to that add-on's place in the cascade (rule 3 above). Otherwise it goes after all add-ons (rule 4). - **Each call** adds one `<style>`. With `data-nonce`, it carries the nonce, so a strict CSP allows it ([CSP](publishing.html#csp)). - A schema entry's `css` goes through `tern.style`. - **Under node** it does nothing and returns nothing. ### Dark mode {#dark-mode} - **The palette** follows the reader's system setting: `tern.css` sets the dark values of the colour properties inside `@media (prefers-color-scheme: dark)`. - **The browser's own parts.** tern.js adds `<meta name="color-scheme" content="light dark">` unless the head has one, so form controls and scrollbars match. - **Restyling dark mode only:** set your values inside the same media query: ```css @media (prefers-color-scheme: dark) { :root { --t-bg: #0d1117; --t-link: #79c0ff; } } ``` - **A property set outside a media query holds in both modes**, since your CSS comes later. Set some colours that way and not the others, and the others still switch: light text can end up on your light background. Set the whole palette, or set it per mode. - **One palette for every reader:** set every colour property at the top level, and `color-scheme: light` (or `dark`) on `:root`. A `color-scheme` key in `:::meta`, or a `<meta name="color-scheme">` in the head, sets only the browser's own parts: `tern.css` still follows the system setting. ### Print {#print} `tern.css` has a print stylesheet: - the colours are black on white, with `color-scheme: light`, and `--t-size` is `11pt`; - the text column has no maximum width, and the body no padding; - code wraps, and tables, code and equations no longer scroll; - the diagnostics panel is hidden; - KaTeX's formulas stay in their sentences in the PDF's text. Before printing, tern.js opens every `details.t-block` (closing them again afterwards), and typesets every formula still waiting. To change print, write `@media print` rules. A property you set at the top level of your CSS also wins over the print values: give it a print value too. ```css @media print { :root { --t-size: 10pt; --t-link: #000; } .callout-toggle { display: none; } } ``` ## Labels in other languages {#languages} ### Language maps {#label-maps} A `label` can be a map from language tags to words: ```js tern.block('lemma', { counter: 'theorem', label: { en: 'Lemma', de: 'Hilfssatz', fr: 'Lemme', 'pt-BR': 'Lema' } }); ``` The label is picked when the note is rendered, and the reference text follows it: in a German note, `:::lemma{#l}` is "Hilfssatz 1", and so is `@l`. ### How the language is chosen {#choosing-language} In the browser, and in `tern check`, `tern build` and the language server, the first of: 1. `data-lang` on the tern.js tag; 2. `window.TERN.lang`; 3. `lang` in a top-level `:::meta`; 4. `lang` on `<html>` in the head. When the head's `<html lang>` and `:::meta` disagree, the head wins, with `meta.conflict` ([Metadata](elements.html#metadata)). In your own node script, `tern.toHTML`, `tern.check` and `tern.transform` read their `lang` option, then `:::meta`, then the `<html lang>` of their `head` option. ### Matching an entry {#matching} Language tags compare without regard to case. Given the language, the map's entry is the first that matches: 1. the exact tag: `pt-BR` for `pt-BR`; 2. its primary subtag: `pt` for `pt-BR`; 3. any entry with that primary subtag: `pt-PT` for `pt-BR`; 4. `en`; 5. the map's first entry. With no language at all, `en`, then the first entry. Values that are not strings are skipped. **A label function** receives no language. To translate a computed label, keep a map of words and pick from it yourself, or use a map and no function. ## The demo schema {#demo-schema} The live examples with `schema=demo`, on this page and every other, render with this schema.
